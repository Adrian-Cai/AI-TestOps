# AI TestOps 主流程压测计划

日期：2026-05-16

## 1. 目标与范围

本次压测只覆盖主业务链路中不依赖大模型的部分：

```text
文件上传 -> 文档解析 -> 人工确认草稿 -> 保存正式用例 -> JSON/Excel 导出
```

不纳入本次压测计时范围的步骤：

- 提取结构化需求：`POST /api/ai-testops/ai/requirements/extract`
- 生成测试用例草稿：`POST /api/ai-testops/testcases/generate`

这两个步骤依赖大模型，耗时主要由外部模型服务、网络和 token 数决定，和当前 Spring Boot 服务的基础容量不是同一类指标。建议单独做“AI 端到端耗时评估”，不要和本次后端压测混在一起。

## 2. 当前机器与容量判断

服务器配置：

| 项目 | 配置 |
| --- | --- |
| CPU | 4 核 |
| 内存 | 4 GB |
| 系统盘 | SSD 云硬盘 70 GB，当前已用 34.2 GB，48.9% |
| 公网带宽 | 6 Mbps，约 0.75 MB/s |
| 当前 CPU | 5.416% |
| 当前内存 | 2325.833 MB，剩余约 1.7 GB |

容量判断：

- 这是一台入门型实例，适合验证 MVP/Demo 的主流程承载能力，不适合按高并发生产系统标准压测。
- 内存余量不大，文档解析和 Excel 导出都会产生短时内存压力。
- 6 Mbps 带宽是导出下载场景的硬上限。Excel/JSON 批量下载的 QPS 会先被带宽限制，而不是先被 CPU 限制。
- 上传文件如果走公网，也要按公网链路做保守估算；如果压测机在同 VPC 内，上传侧结果会比公网乐观。

## 3. 接口映射

| 流程步骤 | 接口 | 说明 |
| --- | --- | --- |
| 文件上传 | `POST /api/ai-testops/documents/upload` | multipart 文件上传，保存文件和 document 记录 |
| 文档解析 | `POST /api/ai-testops/documents/{documentId}/parse` | 调 Apache Tika，清洗文本，切分 chunks，落库 |
| 草稿列表 | `GET /api/ai-testops/testcases/drafts` | 人工确认前可用于查询草稿，不作为主要压测点 |
| 单条确认 | `POST /api/ai-testops/testcases/drafts/{draftCaseId}/approve` | 草稿写入正式用例并记录 review |
| 批量确认 | `POST /api/ai-testops/testcases/drafts/batch-approve` | 推荐作为人工确认压测入口 |
| 用例查询 | `GET /api/ai-testops/testcases` | 导出前查询正式用例 |
| JSON 导出 | `GET /api/ai-testops/export/testcases/json` | 下载正式用例 JSON |
| Excel 导出 | `GET /api/ai-testops/export/testcases/excel` | 使用 Apache POI 生成 xlsx，CPU/内存更敏感 |

## 4. 如何跳过大模型步骤

推荐做法：把 AI 步骤变成“压测前置造数”，不进入压测计时。

### 方案 A：使用 MOCK/离线造数准备草稿

1. 在非压测计时阶段使用 `AI_PROVIDER=MOCK` 或测试数据准备脚本生成 document、requirement extract、draft。
2. 导出待确认草稿 ID，生成 `scripts/perf/draft-groups.json`。
3. 正式压测时只调用：
   - `POST /api/ai-testops/testcases/drafts/batch-approve`
   - `GET /api/ai-testops/export/testcases/json`
   - `GET /api/ai-testops/export/testcases/excel`

### 方案 B：直接写入压测草稿数据

如果想完全避开 AI 生成接口，可以直接向以下表插入压测数据：

- `ai_testops_document`
- `ai_testops_document_parse_result`
- `ai_testops_document_chunk`
- `ai_testops_generation_record`
- `ai_testops_test_case_draft`

关键要求：

- `ai_testops_test_case_draft.review_status` 必须是 `PENDING`。
- 每次压测确认使用的 `draft_case_id` 必须唯一，不要重复消费同一个草稿。
- `steps_json` 必须是非空 JSON 数组，元素至少包含 `step_no` 和 `action`。
- `expected_results_json` 必须是非空 JSON 字符串数组。

`scripts/perf/draft-groups.example.json` 的格式如下：

```json
[
  {
    "documentId": "DOC_20260516_000001",
    "draftCaseIds": ["DRAFT_20260516_000001", "DRAFT_20260516_000002"],
    "reviewer": "perf_user"
  }
]
```

数据量建议：

- 如果每个请求批量确认 5 条草稿，跑 `5 QPS * 10 分钟`，至少需要 `5 * 600 = 3000` 组草稿，也就是 `15000` 条 `PENDING` 草稿。
- 如果只是基线验证，可以先准备 300 到 1000 条草稿。

## 5. 压测场景设计

### 场景 1：文件上传 + 文档解析

目的：验证批量用户上传需求文档并解析时，应用、磁盘、数据库和 Tika 的承载能力。

建议文件模型：

| 文件类型 | 大小 | 用途 |
| --- | --- | --- |
| md/txt | 50 KB 到 300 KB | 日常轻量需求文档基线 |
| pdf/docx/xlsx | 300 KB 到 1 MB | 常见办公文档 |
| pdf/docx/xlsx | 3 MB 到 5 MB | 小规模边界场景 |

第一轮不要直接压 50 MB 上限文件。50 MB 更适合做单独的极限/异常场景，不适合代表主流程。

### 场景 2：人工批量确认 + 导出

目的：验证 AI 已生成草稿后，人工确认、正式用例保存、JSON/Excel 导出的吞吐。

建议模型：

- 每个请求批量确认 5 条草稿。
- 每个 document 对应 20 到 100 条草稿。
- 确认完成后按 `documentId` 导出 JSON 和 Excel。
- 压测数据必须按批次隔离，避免多个虚拟用户确认同一批草稿。

### 场景 3：混合主流程

建议先分场景压测，再做混合压测。混合流量比例可先按：

| 动作 | 占比 |
| --- | --- |
| 上传 + 解析 | 40% |
| 批量确认 | 40% |
| JSON/Excel 导出 | 20% |

如果真实使用中“批量下载到本地”很多，把导出比例提升到 30%，并单独观察公网带宽。

## 6. QPS 与响应时间目标

基于当前 4C4G、6 Mbps、Spring Boot + MariaDB + 本地磁盘上传目录的配置，建议把下面指标作为第一版合理目标。

| 场景 | 建议通过 QPS | 表现较好 QPS | 平均响应 | P95 | P99 | 错误率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 到 300 KB 文件上传 | 2 到 3 | 5 | <= 500 ms | <= 1 s | <= 2 s | < 1% |
| 100 到 300 KB md/txt 解析 | 2 | 3 到 5 | <= 1 s | <= 2.5 s | <= 5 s | < 1% |
| 300 KB 到 1 MB Office/PDF 解析 | 1 | 2 | <= 2 s | <= 5 s | <= 8 s | < 1% |
| 批量确认，5 条草稿/请求 | 5 | 8 到 10 | <= 500 ms | <= 1.2 s | <= 2.5 s | < 1% |
| JSON 导出，约 50 条用例 | 3 | 5 | <= 600 ms | <= 1.2 s | <= 2.5 s | < 1% |
| Excel 导出，约 50 条用例 | 1 到 2 | 3 | <= 1.2 s | <= 2.5 s | <= 5 s | < 1% |
| 混合主流程，不含 AI | 3 | 5 | <= 1 s | <= 3 s | <= 6 s | < 1% |

解释：

- 当前机器如果混合主流程能稳定 `3 QPS`，已经可以说明 Demo 主流程可用。
- 如果能稳定 `5 QPS`，且 CPU 平均低于 70%、内存无持续增长、错误率低于 1%，对这台入门实例来说表现较好。
- 如果冲到 `8 到 10 QPS` 后 P99 明显拉长，通常是合理现象；需要看瓶颈是带宽、Tika、数据库连接池、磁盘还是 Excel 生成。
- 大文件上传/导出不能只看 QPS，必须同时看吞吐量 MB/s。

## 7. 带宽限制估算

6 Mbps 约等于 0.75 MB/s。考虑协议开销和波动，建议只按 60% 到 70% 可用带宽估算：

```text
保守可用吞吐 = 0.75 MB/s * 0.6 = 0.45 MB/s
可承载 QPS ~= 0.45 / 单次响应或文件大小(MB)
```

示例：

| 单次下载大小 | 保守可承载导出 QPS |
| ---: | ---: |
| 100 KB，约 0.1 MB | 约 4.5 QPS |
| 500 KB，约 0.5 MB | 约 0.9 QPS |
| 1 MB | 约 0.45 QPS |
| 5 MB | 约 0.09 QPS |

所以“批量下载到本地”场景不要只用请求数判断容量。导出文件越大，公网带宽越快成为瓶颈。

## 8. 阶段计划

| 阶段 | 目标 | 配置建议 | 通过标准 |
| --- | --- | --- | --- |
| 预热 | 让 JVM、连接池、缓存进入稳定状态 | 1 QPS，5 分钟 | 无明显错误 |
| 基线 | 建立当前机器基础数据 | 2 QPS，10 分钟 | P95 达标，错误率 < 1% |
| 目标 | 验证合理业务目标 | 3 到 5 QPS，15 分钟 | CPU < 70%，内存稳定，P99 达标 |
| 阶梯 | 找拐点 | 5、8、10 QPS，每档 10 分钟 | 找到 P99 或错误率突增点 |
| 稳定性 | 看长时间波动 | 目标 QPS，30 到 60 分钟 | 无内存持续上涨，无磁盘异常增长 |

## 10. 监控项

压测期间至少记录：

- 应用接口：QPS、平均响应、P95、P99、错误率。
- 服务器：CPU、内存、磁盘剩余空间、磁盘 IO、公网入/出带宽。
- JVM：堆内存、GC 次数和耗时、线程数。
- 数据库：连接数、慢 SQL、锁等待、CPU、IO。
- 应用日志：`BusinessException`、Tika parse failed、Excel export failed、数据库连接异常。

建议暂停条件：

- 错误率连续 3 分钟超过 5%。
- CPU 连续 5 分钟超过 90%。
- 内存持续上涨且无法回落。
- 磁盘剩余空间低于 15 GB。
- P99 超过目标 2 倍并持续 5 分钟。

## 12. 第一轮建议结论口径

在当前配置下，第一轮可把目标定为：

- 主流程混合场景：`3 QPS` 必须稳定，`5 QPS` 算表现较好。
- 批量确认接口：`5 QPS` 必须稳定，`8 到 10 QPS` 算表现较好。
- Excel 导出：按 50 条用例的文件大小看，`1 到 2 QPS` 稳定即可；文件超过 500 KB 后优先按带宽吞吐评估。
- 文件上传和解析：300 KB 以内文档看 `2 到 3 QPS`，1 MB 左右文档看 `1 QPS` 是否稳定。

如果这些目标都达标，再考虑升级到 2C/4C 更高内存、提高公网带宽、异步解析、导出文件缓存、限流和队列化等优化项。
