
要实现 Diff 分析功能，**需要一个真实项目仓库作为分析对象**。因为 Diff 分析的前提就是：系统要知道某个需求对应的代码分支，相对于 `master/main` 分支到底改了哪些文件、哪些方法、哪些逻辑。

把整个验证流程设计成这样：

```text
1. 有一个需求文档
2. AI 根据需求文档生成测试用例，并落库
3. 开发从 master 拉出 feature 分支
4. 开发在 feature 分支实现需求
5. 开发提交代码，准备合并回 master
6. 平台获取 feature 分支和 master 分支的 Diff
7. 平台分析本次代码改动点
8. 平台查询该需求下已经生成的测试用例
9. 平台判断这些测试用例是否覆盖本次代码变更风险
10. 未覆盖的风险生成补充用例
11. 输出合并准入报告
```

---

# 一、需要先准备一个项目仓库

建议就用现在的 AI TestOps 项目作为实验仓库。

比项目可以有这样的分支：

```text
master
feature/requirement-case-generation
feature/diff-risk-analysis
feature/add-case-review
feature/add-merge-gate-report
```

Diff 分析功能就是分析：

```text
feature/diff-risk-analysis  vs  master
```

或者分析：

```text
feature/add-case-review  vs  master
```

也就是说，自己开发这个平台时，每做一个功能，就可以用它来反向验证你的 Diff 分析能力。

这非常适合作为作品闭环。

---

# 二、推荐你用“真实需求 → 真实分支 → 真实 Diff”来验证

不要一开始用假数据。你可以设计一个小需求，例如：

```text
需求：支持 Diff 分析任务创建

功能说明：
用户输入仓库地址、源分支、目标分支后，系统创建 Diff 分析任务，并记录任务状态。
```

然后你根据这个需求生成测试用例。

用例可能包括：

```text
1. 正常创建 Diff 分析任务
2. 源分支为空时提示错误
3. 目标分支为空时默认 master
4. 仓库地址非法时创建失败
5. 重复提交同一分支分析任务时如何处理
6. 创建成功后任务状态为 PENDING
```

然后你新建分支：

```bash
git checkout master
git pull
git checkout -b feature/diff-analysis-task
```

在这个分支里实现：

```text
DiffAnalysisTaskController
DiffAnalysisTaskService
DiffAnalysisTaskRepository
ai_testops_diff_analysis_task 表
创建任务接口
```

开发完成后，你的 Diff 分析工具就可以分析：

```bash
git diff master...feature/diff-analysis-task
```

然后平台应该识别出：

```text
1. 新增 Diff 分析任务接口
2. 新增任务创建逻辑
3. 新增数据库表操作
4. 涉及分支参数校验
5. 涉及任务状态初始化
6. 潜在风险：参数校验不足、状态流转错误、重复任务处理缺失、仓库地址安全风险
```

再去匹配你之前 AI 生成的用例，判断哪些已覆盖、哪些未覆盖。

# 三、这才是你 Diff 分析工具的真实闭环

你要验证的不是“能不能拿到 Diff”，而是这条链路：

```text
需求生成用例
  ↓
开发实现需求
  ↓
代码 Diff 识别风险
  ↓
已有用例覆盖匹配
  ↓
发现遗漏测试点
  ↓
补充用例
  ↓
合并准入
```

举个更具体的例子。

---

## 需求阶段

需求文档：

```text
用户可以创建 Diff 分析任务。
用户需要输入仓库地址、源分支、目标分支。
系统需要校验参数是否合法。
创建成功后任务状态为 PENDING。
```

AI 生成用例：

```text
TC001：正常创建 Diff 分析任务
TC002：仓库地址为空时创建失败
TC003：源分支为空时创建失败
TC004：目标分支为空时默认 master
TC005：创建成功后任务状态为 PENDING
```

---

## 开发阶段

代码中你实际实现了：

```text
1. 新增创建任务接口
2. 校验 repoUrl 不能为空
3. 校验 sourceBranch 不能为空
4. targetBranch 为空时默认 master
5. 写入数据库任务状态为 PENDING
6. 但没有处理重复任务
```

---

## Diff 分析阶段

平台分析代码后发现：

```text
风险1：重复创建同一 sourceBranch + targetBranch 的任务可能产生重复数据
风险2：repoUrl 只校验非空，没有校验协议是否合法
风险3：sourceBranch 没有校验是否真实存在
风险4：任务状态初始化依赖硬编码，后续状态流转需要验证
```

然后去查已有测试用例。

匹配结果：

| 风险                     | 已有用例是否覆盖 | 结果          |
| ---------------------- | -------- | ----------- |
| repoUrl 为空校验           | 已覆盖      | COVERED     |
| sourceBranch 为空校验      | 已覆盖      | COVERED     |
| targetBranch 默认 master | 已覆盖      | COVERED     |
| 状态初始化为 PENDING         | 已覆盖      | COVERED     |
| 重复任务创建                 | 未覆盖      | NOT_COVERED |
| 分支是否真实存在               | 未覆盖      | NOT_COVERED |
| repoUrl 协议合法性          | 未覆盖      | NOT_COVERED |

然后系统生成补充用例：

```text
TC006：重复创建同一分支 Diff 分析任务时应提示已存在或复用原任务
TC007：sourceBranch 不存在时创建任务失败
TC008：repoUrl 非 Git 地址时创建任务失败
```

这就是完整闭环。

# 四、你应该怎么组织开发分支？

推荐你按照真实企业流程来做。

```text
master
  ↓
feature/ai-case-generation
  ↓
feature/diff-analysis-task
  ↓
feature/diff-changed-file-parser
  ↓
feature/diff-risk-analysis
  ↓
feature/diff-case-coverage
  ↓
feature/merge-gate-report
```

每个分支都对应一个需求。

每个需求都先走：

```text
需求文档 → AI 生成测试用例 → 测试用例落库
```

然后开发完成后走：

```text
代码 Diff → 风险分析 → 用例覆盖匹配
```

这样你就能用自己的项目持续训练和验证这套能力。

## 需求 1：创建 Diff 分析任务


目标：验证 Git Diff 获取能力。

开发内容：

Diff 分析重点：


---

## 需求 3：风险与已有用例匹配

目标：验证你的核心价值能力。

开发内容：


Diff 分析重点：


# 六、你的平台入口应该怎么设计？

创建 Diff 分析任务时，页面最好让用户选择：

```text
关联需求：
关联文档：
仓库地址：
目标分支：master
源分支：feature/xxx
是否启用 AI 风险分析：
是否启用用例覆盖匹配：
是否生成补充用例：
```

核心是必须绑定：

```text
Diff 分析任务 ↔ 需求/文档 ↔ 已生成用例
```

如果不绑定需求，平台也能分析代码风险，但无法准确知道应该拿哪些测试用例去匹配。

# 八、什么时候触发 Diff 分析？

你有三种触发方式。

## 方式一：手动触发，最适合 MVP

页面输入：

```text
repoUrl
sourceBranch
targetBranch
documentId / requirementExtractId
```

点击：

```text
开始 Diff 分析
```

这个最简单，建议你第一版就做这个。

---

## 方式二：Pull Request / Merge Request 触发

开发创建 PR 后，平台自动分析：

```text
PR source branch vs target branch
```

然后把风险报告发到 PR 评论里。

这是第二阶段目标。

---

## 方式三：CI/CD 门禁触发

合并前流水线自动调用你的平台：

```text
POST /api/diff-analysis/tasks
```

如果返回：

```text
BLOCK
```

则阻止合并。

这是第三阶段目标。

# 九、你现在应该怎么落地？

建议你现在就按这个顺序做：

```text
第一步：准备一个真实 Git 仓库
第二步：写一个简单需求文档
第三步：用你已有功能生成测试用例并落库
第四步：从 master 拉 feature 分支

第九步：生成风险项和覆盖关系
第十步：输出准入报告
```

这条链路跑通以后，你的 AI TestOps 项目就有了真正的闭环。

# 十、最终结论

是的，要实现 Diff 分析，你最好有一个真实项目仓库，并且按照真实研发流程来做：

```text
master 拉分支
  ↓
实现某个需求
  ↓
提交代码
  ↓
准备合并 master
  ↓
执行 Diff 分析
  ↓
对比需求阶段已生成测试用例
  ↓
识别未覆盖风险
```

这个流程不仅能帮助你实现功能，也能让你的平台本身成为演示案例。

你可以把它包装成：

> 使用 AI TestOps 平台自身的开发过程作为样例：需求阶段自动生成测试用例，代码提交阶段自动分析 Diff 风险，并校验测试用例覆盖情况，最终输出合并准入报告。
