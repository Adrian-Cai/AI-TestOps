# 需求文档：代码 Diff 分析与测试覆盖风险识别功能

## 1. 需求背景

当前 AI TestOps 平台已经支持根据需求文档自动生成测试用例，并将测试用例保存到数据库中。测试人员可以基于需求阶段生成的测试用例进行评审、修改和沉淀。

但是在实际研发过程中，开发人员完成需求后，会基于 `master` 分支拉取新的开发分支进行编码实现。代码开发完成后，在合并回 `master` 分支之前，测试人员需要判断本次代码改动是否已经被需求阶段生成的测试用例覆盖。

目前存在以下问题：

1. 测试人员需要人工查看代码 Diff，分析成本高。
2. 测试人员不一定能准确理解代码变更对业务场景的影响。
3. 需求阶段生成的测试用例可能无法完全覆盖实际代码实现中的边界场景、异常场景和潜在风险。
4. 代码合并前缺少自动化的风险识别和测试覆盖校验机制。
5. 对于未覆盖的风险点，缺少补充测试用例和风险闭环处理能力。

因此，需要新增一个 **代码 Diff 分析与测试覆盖风险识别功能**，用于在代码合并前自动分析分支变更，识别潜在测试风险，并与已有测试用例进行覆盖匹配。

---

## 2. 需求目标

本功能目标是在开发分支合并到 `master` 分支前，基于代码 Diff 自动识别本次代码变更带来的风险，并判断这些风险是否已经被已有测试用例覆盖。

系统需要支持：

1. 用户创建代码 Diff 分析任务。
2. 用户输入仓库地址、源分支、目标分支，并关联已有需求或需求解析结果。
3. 系统自动获取源分支相对于目标分支的代码 Diff。
4. 系统解析本次变更文件、变更类型、变更行数和变更摘要。
5. 系统基于规则和大模型识别代码变更风险。
6. 系统查询该需求下已经生成并落库的测试用例。
7. 系统判断已有测试用例是否覆盖代码变更风险。
8. 对于未覆盖或部分覆盖的风险，系统生成补充测试建议或补充测试用例。
9. 系统输出合并准入报告，给出 `PASS`、`WARNING`、`BLOCK` 或 `MANUAL_REVIEW` 结论。
10. 系统记录风险处理动作，形成风险闭环。

---

## 3. 业务流程

### 3.1 需求阶段

1. 用户上传或输入需求文档。
2. 系统解析需求文档。
3. 系统调用大模型生成测试用例。
4. 测试人员评审测试用例。
5. 测试用例确认后落库，成为正式测试用例。

### 3.2 开发阶段

1. 开发人员从 `master` 分支拉取新的开发分支。
2. 开发人员在新分支上实现需求。
3. 开发完成后提交代码。
4. 开发人员准备将新分支合并回 `master` 分支。

### 3.3 Diff 分析阶段

1. 用户进入代码 Diff 分析页面。
2. 用户选择或输入：

   * 仓库地址
   * 源分支
   * 目标分支
   * 关联需求
   * 关联需求解析结果
3. 用户点击“开始分析”。
4. 系统创建 Diff 分析任务。
5. 系统获取源分支与目标分支之间的代码 Diff。
6. 系统解析变更文件和变更内容。
7. 系统识别代码变更风险。
8. 系统查询该需求下已有测试用例。
9. 系统判断风险是否被已有测试用例覆盖。
10. 系统生成风险清单和覆盖分析结果。
11. 系统输出合并准入报告。

### 3.4 风险闭环阶段

1. 对于已覆盖风险，系统标记为 `COVERED`。
2. 对于部分覆盖风险，系统标记为 `PARTIAL_COVERED`，并给出补充测试建议。
3. 对于未覆盖风险，系统标记为 `NOT_COVERED`，并支持生成补充测试用例。
4. 测试人员可以确认风险、忽略风险、关联已有用例、生成补充用例或标记验证结果。
5. 系统记录风险处理动作。
6. 所有高风险未覆盖项处理完成后，系统重新计算合并准入结论。

## 4. 功能范围

### 4.1 本期实现范围

本期实现 MVP 版本，包含以下功能：

1. 创建 Diff 分析任务。
2. 获取分支 Diff。
3. 保存变更文件信息。
4. 基于规则识别初步风险。
5. 调用大模型分析变更风险。
6. 查询已有测试用例。
7. 判断风险与测试用例覆盖关系。
8. 保存风险项。
9. 保存风险与用例关联关系。
10. 生成合并准入报告。
11. 支持对未覆盖风险生成补充测试用例。
12. 支持风险处理状态流转。

### 4.2 本期暂不实现范围

以下能力本期暂不实现：

1. 自动阻断真实代码合并。
2. 自动在 GitHub / GitLab PR 中评论分析结果。
3. 完整 AST 调用链分析。
4. 自动执行所有测试用例。
5. 与 Jira、禅道等缺陷系统深度集成。
6. 多仓库跨服务影响分析。
7. 生产流量回放分析。

## 7. 功能详细说明

### 7.1 创建 Diff 分析任务

#### 功能描述

用户输入仓库地址、源分支、目标分支并关联需求后，系统创建一条 Diff 分析任务。

#### 输入字段

```json id="7lgslb"
{
  "documentId": 1001,
  "requirementExtractId": 2001,
  "repoUrl": "git@github.com:acai1998/AI-TestOps.git",
  "sourceBranch": "feature/diff-analysis",
  "targetBranch": "master",
  "analysisOptions": {
    "includeTestFiles": false,
    "enableAiAnalysis": true,
    "enableCoverageCheck": true,
    "autoGenerateSupplementCases": false
  }
}
```

#### 业务规则

1. 仓库地址不能为空。
2. 源分支不能为空。
3. 目标分支不能为空，默认值为 `master`。
4. 关联需求不能为空。
5. 同一个仓库、源分支、目标分支在存在运行中任务时，不允许重复创建。
6. 创建任务后，任务状态为 `PENDING`。
7. 任务开始执行后，状态变更为 `RUNNING`。
8. 任务执行成功后，状态变更为 `SUCCESS`。
9. 任务执行失败后，状态变更为 `FAILED`，并记录失败原因。

---

### 7.2 获取代码 Diff

#### 功能描述

系统根据用户输入的源分支和目标分支，获取两个分支之间的代码差异。

#### 业务规则

1. 系统需要先拉取最新远程分支信息。
2. 如果仓库地址无效，任务失败。
3. 如果源分支不存在，任务失败。
4. 如果目标分支不存在，任务失败。
5. 系统需要获取变更文件列表。
6. 系统需要获取每个变更文件的 Diff Patch。
7. 系统需要统计新增行数、删除行数和总变更行数。
8. 默认不分析测试文件。
9. 如果用户选择包含测试文件，则需要将测试文件纳入分析范围。

#### 变更类型

| 类型         | 说明    |
| ---------- | ----- |
| `ADDED`    | 新增文件  |
| `MODIFIED` | 修改文件  |
| `DELETED`  | 删除文件  |
| `RENAMED`  | 重命名文件 |

---

### 7.3 解析变更文件

#### 功能描述

系统根据文件路径、文件后缀和文件内容识别变更文件角色。

#### 文件角色识别规则

| 文件特征                                | 文件角色         |
| ----------------------------------- | ------------ |
| 路径包含 `controller`                   | `CONTROLLER` |
| 路径包含 `service`                      | `SERVICE`    |
| 路径包含 `mapper`、`dao`、`repository`    | `DAO`        |
| 文件后缀为 `.sql`                        | `SQL`        |
| 文件后缀为 `.yml`、`.yaml`、`.properties`  | `CONFIG`     |
| 路径包含 `job`、`scheduler`              | `JOB`        |
| 路径包含 `mq`、`consumer`、`producer`     | `MQ`         |
| 路径包含 `auth`、`security`、`permission` | `AUTH`       |
| 路径包含 `test`                         | `TEST`       |
| 其他                                  | `OTHER`      |

---

### 7.4 初步风险规则识别

#### 功能描述

系统基于规则引擎对变更文件进行初步风险识别。

#### 默认风险规则

| 规则               | 风险等级     | 风险分类  | 说明                |
| ---------------- | -------- | ----- | ----------------- |
| 修改 Controller 文件 | `MEDIUM` | 接口兼容  | 可能影响接口入参、出参或权限    |
| 修改 Service 文件    | `HIGH`   | 业务逻辑  | 可能影响核心业务流程        |
| 修改 DAO/Mapper 文件 | `HIGH`   | 数据一致性 | 可能影响数据库读写逻辑       |
| 修改 SQL 文件        | `HIGH`   | 数据结构  | 可能影响表结构、数据兼容和回滚   |
| 修改配置文件           | `MEDIUM` | 配置风险  | 可能影响环境配置、开关和依赖    |
| 修改权限相关文件         | `HIGH`   | 权限风险  | 可能产生越权或权限遗漏       |
| 修改 MQ 相关文件       | `HIGH`   | 异步消息  | 可能产生重复消费、漏消费或幂等问题 |
| 修改定时任务           | `MEDIUM` | 调度风险  | 可能影响任务执行时间和重复执行   |
| 单文件变更超过 300 行    | `HIGH`   | 大变更风险 | 变更范围较大，测试遗漏概率较高   |
| 删除文件             | `HIGH`   | 兼容性风险 | 可能影响依赖该文件的功能      |

---

### 7.5 大模型语义风险分析

#### 功能描述

系统将需求背景、变更文件摘要、核心 Diff 内容和历史测试用例作为输入，调用大模型分析代码变更带来的业务风险。

#### 输入内容

1. 需求解析结果。
2. 需求阶段生成的测试用例摘要。
3. 变更文件列表。
4. 变更文件 Diff 摘要。
5. 初步规则风险。
6. 历史缺陷信息，当前版本可选。

#### 输出内容

```json id="5ndhr8"
{
  "riskList": [
    {
      "riskTitle": "分支不存在时任务失败处理可能未覆盖",
      "riskLevel": "HIGH",
      "riskCategory": "异常场景",
      "affectedModule": "Diff分析任务创建",
      "affectedScenarios": [
        "源分支不存在",
        "目标分支不存在"
      ],
      "riskReason": "系统需要调用Git获取分支Diff，如果分支不存在但没有明确错误处理，任务可能异常中断。",
      "testSuggestion": "需要补充源分支不存在、目标分支不存在的异常测试。",
      "missingTestScenarios": [
        "sourceBranch不存在时任务状态应为FAILED",
        "targetBranch不存在时任务状态应为FAILED"
      ]
    }
  ]
}
```

#### 业务规则

1. 大模型输出必须为结构化 JSON。
2. 风险等级只能为 `HIGH`、`MEDIUM`、`LOW`。
3. 风险分类必须从系统预设分类中选择。
4. 如果大模型输出无法解析，任务不能整体失败，应记录 AI 分析失败原因，并保留规则风险结果。
5. 大模型分析结果需要保存到风险项表。
6. 同一个任务下相同风险编码不能重复保存。

---

### 7.6 查询已有测试用例

#### 功能描述

系统根据关联需求查询已经生成并落库的测试用例。

#### 查询范围

优先查询：

1. 当前需求关联的正式测试用例。
2. 当前需求对应的需求-用例映射关系。
3. 当前文档生成的正式测试用例。

扩展查询：

1. 同模块历史测试用例。
2. 相同接口相关测试用例。
3. 相同风险标签测试用例。
4. 人工补充测试用例。

#### 业务规则

1. 只查询状态有效的正式测试用例。
2. 草稿用例默认不参与覆盖匹配。
3. 被驳回的用例不参与覆盖匹配。
4. 如果当前需求下没有正式测试用例，需要提示“当前需求暂无可用于覆盖匹配的测试用例”。
5. 没有已有用例时，所有风险默认标记为 `NOT_COVERED`。

---

### 7.7 风险与测试用例覆盖匹配

#### 功能描述

系统将风险项与已有测试用例进行匹配，判断已有测试用例是否覆盖代码变更风险。

#### 覆盖状态

| 状态                | 说明            |
| ----------------- | ------------- |
| `COVERED`         | 已有用例能够覆盖该风险   |
| `PARTIAL_COVERED` | 已有用例只覆盖部分场景   |
| `NOT_COVERED`     | 没有用例覆盖该风险     |
| `NEED_CONFIRM`    | 系统无法确定，需要人工确认 |

#### 匹配依据

1. 用例标题。
2. 用例步骤。
3. 预期结果。
4. 用例标签。

### 7.8 生成补充测试用例

#### 功能描述

对于 `NOT_COVERED` 或 `PARTIAL_COVERED` 的风险，系统支持生成补充测试用例。

#### 生成条件

满足以下任一条件时，可以生成补充测试用例：

1. 风险覆盖状态为 `NOT_COVERED`。
2. 风险覆盖状态为 `PARTIAL_COVERED`。
3. 测试人员手动点击“生成补充用例”。

#### 补充用例来源标记

补充用例保存到正式测试用例表或草稿表时，需要标记来源：

```text id="lfmbpt"
source_type = DIFF_SUPPLEMENT
source_id = risk_id
```

#### 业务规则

1. 生成补充用例前，需要校验风险是否存在。
2. 已关闭风险不允许生成补充用例。
3. 已忽略风险不允许生成补充用例。
4. 生成的补充用例需要与风险建立关联关系。
5. 生成补充用例后，风险处理状态变更为 `WAIT_TEST`。
6. 生成补充用例的操作需要记录到风险处理动作表。
7. 补充用例需要进入人工评审流程。

### 7.9 风险处理状态流转

#### 风险处理状态

| 状态          | 说明    |
| ----------- | ----- |
| `PENDING`   | 待确认   |
| `CONFIRMED` | 已确认   |
| `IGNORED`   | 已忽略   |
| `WAIT_CASE` | 待补充用例 |
| `WAIT_TEST` | 待执行测试 |
| `TESTING`   | 验证中   |
| `PASSED`    | 验证通过  |
| `FAILED`    | 验证失败  |
| `BLOCKED`   | 验证阻塞  |
| `CLOSED`    | 已关闭   |

#### 状态流转规则

1. 新生成风险默认为 `PENDING`。
2. 用户点击确认风险后，状态变更为 `CONFIRMED`。
3. 用户点击忽略风险后，状态变更为 `IGNORED`，必须填写忽略原因。
4. 未覆盖风险确认后，状态变更为 `WAIT_CASE`。
5. 生成或关联测试用例后，状态变更为 `WAIT_TEST`。
6. 测试执行开始后，状态变更为 `TESTING`。
7. 测试通过后，状态变更为 `PASSED`。
8. 测试失败后，状态变更为 `FAILED`。
9. 无法验证时，状态变更为 `BLOCKED`。
10. 风险处理完成后，状态变更为 `CLOSED`。
11. 每一次状态变化都需要记录操作人、操作时间、操作说明和状态变化前后值。

### 7.10 合并准入报告

#### 功能描述

系统根据本次 Diff 分析结果、风险覆盖情况和风险处理状态生成合并准入报告。

#### 准入状态规则

| 条件            | 准入状态            |
| ------------- | --------------- |
| 存在高风险未覆盖项     | `BLOCK`         |
| 存在高风险验证失败项    | `BLOCK`         |
| 存在阻塞状态风险      | `BLOCK`         |
| 存在中风险未覆盖项     | `WARNING`       |
| 存在需要人工确认的风险   | `MANUAL_REVIEW` |
| 所有风险均已覆盖或验证通过 | `PASS`          |

#### 报告内容

1. 任务基本信息。
2. 仓库地址。
3. 源分支。
4. 目标分支。
5. 变更文件数量。
6. 变更方法数量。
7. 高风险数量。
8. 中风险数量。
9. 低风险数量。
10. 已覆盖风险数量。
11. 部分覆盖风险数量。
12. 未覆盖风险数量。
13. 阻塞风险数量。
14. 建议补充用例数量。
15. 建议回归模块。
16. 准入状态。
17. 准入原因。
18. 风险明细。

## 8. 异常场景

### 8.1 仓库异常

| 场景       | 期望结果                    |
| -------- | ----------------------- |
| 仓库地址为空   | 创建任务失败，提示仓库地址不能为空       |
| 仓库地址格式非法 | 创建任务失败，提示仓库地址格式非法       |
| 仓库无法访问   | 任务状态变更为 `FAILED`，记录失败原因 |
| 仓库认证失败   | 任务状态变更为 `FAILED`，提示认证失败 |

---

### 8.2 分支异常

| 场景         | 期望结果                  |
| ---------- | --------------------- |
| 源分支为空      | 创建任务失败，提示源分支不能为空      |
| 目标分支为空     | 默认使用 `master`         |
| 源分支不存在     | 任务状态变更为 `FAILED`      |
| 目标分支不存在    | 任务状态变更为 `FAILED`      |
| 源分支与目标分支相同 | 创建任务失败，提示源分支不能和目标分支相同 |

---

### 8.3 Diff 异常

| 场景            | 期望结果                      |
| ------------- | ------------------------- |
| 无代码变更         | 任务成功，风险数量为 0，准入状态为 `PASS` |
| Diff 内容过大     | 系统进行摘要截断，不影响任务整体执行        |
| 文件 Patch 获取失败 | 记录文件级失败原因，继续分析其他文件        |
| 二进制文件变更       | 不解析 Patch，只记录文件变更         |

---

### 8.4 AI 分析异常

| 场景          | 期望结果                  |
| ----------- | --------------------- |
| 大模型调用失败     | 保留规则风险结果，记录 AI 失败原因   |
| 大模型输出非 JSON | 尝试修复，修复失败则记录失败原因      |
| 大模型输出空风险    | 保留规则风险，风险来源标记为 `RULE` |
| 大模型超时       | 任务不中断，记录超时信息          |

---

### 8.5 用例覆盖匹配异常

| 场景        | 期望结果                  |
| --------- | --------------------- |
| 当前需求无测试用例 | 风险默认标记为 `NOT_COVERED` |
| 用例数据不完整   | 参与匹配但降低置信度            |
| 覆盖关系无法判断  | 标记为 `NEED_CONFIRM`    |
| 匹配服务异常    | 记录失败原因，允许用户稍后重新匹配     |

## 12. 验收标准

### 12.1 创建任务验收

1. 输入合法仓库地址、源分支、目标分支和关联需求后，可以成功创建 Diff 分析任务。
2. 创建成功后任务状态为 `PENDING`。
3. 开始执行后任务状态变更为 `RUNNING`。
4. 执行成功后任务状态变更为 `SUCCESS`。
5. 执行失败后任务状态变更为 `FAILED`，并记录失败原因。

---

### 12.2 Diff 获取验收

1. 系统可以正确获取源分支相对于目标分支的变更文件列表。
2. 系统可以识别新增、修改、删除、重命名文件。
3. 系统可以统计每个文件的新增行数、删除行数和总变更行数。
4. 系统可以保存每个文件的 Patch 内容。
5. 当无代码变更时，任务成功，风险数量为 0，准入状态为 `PASS`。

---

### 12.3 风险识别验收

1. 修改 Controller 文件时，系统可以识别接口兼容风险。
2. 修改 Service 文件时，系统可以识别业务逻辑风险。
3. 修改 SQL 文件时，系统可以识别数据结构风险。
4. 修改配置文件时，系统可以识别配置风险。
5. 删除文件时，系统可以识别兼容性风险。
6. 系统可以调用大模型生成业务影响场景和测试建议。
7. 大模型异常时，任务不能整体失败。

---

### 12.4 用例覆盖匹配验收

1. 系统可以根据关联需求查询已有正式测试用例。
2. 系统可以将风险项与已有测试用例建立覆盖关系。
3. 系统可以判断风险为已覆盖、部分覆盖、未覆盖或需要人工确认。
4. 未覆盖风险可以生成补充测试用例。
5. 补充测试用例需要与风险建立关联关系。
6. 生成补充用例后，风险状态变更为 `WAIT_TEST`。

---

### 12.5 风险闭环验收

1. 用户可以确认风险。
2. 用户可以忽略风险，且必须填写忽略原因。
3. 用户可以关联已有测试用例。
4. 用户可以生成补充测试用例。
5. 用户可以标记风险验证通过、失败或阻塞。
6. 每次风险处理动作都需要记录操作日志。
7. 风险状态流转符合定义规则。

---

### 12.6 准入报告验收

1. 系统可以生成合并准入报告。
2. 存在高风险未覆盖项时，准入状态为 `BLOCK`。
3. 存在高风险验证失败项时，准入状态为 `BLOCK`。
4. 存在中风险未覆盖项时，准入状态为 `WARNING`。
5. 存在需要人工确认的风险时，准入状态为 `MANUAL_REVIEW`。
6. 所有风险均已覆盖或验证通过时，准入状态为 `PASS`。
7. 报告需要展示风险数量、覆盖情况、建议补充用例数量和准入原因。
