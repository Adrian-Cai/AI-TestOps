当前问题：**CPU/内存不高，但上传接口在压测下出现 `code=500`、响应变慢、业务成功率下降。**

后续压测补充：

- 使用英文文件名仍会出现异常，但异常频率明显降低，说明中文文件名/路径可能放大问题，但不是唯一根因。
- 使用多文件轮询后异常明显增高，说明问题更偏向“高频创建 document / chunk / parse_result 记录”和压测脚本数据配置，而不是单纯同一文件 hash 去重。
- 当前生产 SQL 中 `file_hash` 是普通索引，不是唯一索引；本轮不新增 `file_hash` 唯一约束，也不把重复内容上传改成直接返回已有 document。
- 本轮优先改造：业务 ID 使用 UUID 后缀、上传落盘名改为 `{documentId}.{ext}`、错误响应补充 `traceId`、JMeter 上传 CSV 改为 `filePath,fileName,mimeType` 三列轮询。

# 一、优先判断

当前最像这几类问题：

| 优先级 | 问题类型                      | 现象                     |
| --- | ------------------------- | ---------------------- |
| P0  | 业务 ID 使用日期 + 6 位随机数，压测下 document/chunk/parse_result 唯一键碰撞 | 轮询后创建记录更多，`500` 增多 |
| P0  | 异常被统一包装成“系统异常”，缺少具体错误     | JMeter 只能看到 `code=500` |
| P1  | 上传落盘文件名包含原始文件名            | 英文文件名异常降低，但未完全消失      |
| P1  | JMeter 轮询脚本未明确 filePath/fileName/mimeType | 多文件场景下样本归因不清          |
| P2  | 线程池 / 连接池偏小               | 响应时间变长，但机器资源低          |

---

# 二、第一步：先把错误打出来


后端全局异常不要只返回：

```json
{"code":500,"message":"系统异常","data":null}
```

建议临时改成带 `traceId`：

```json
{
  "code": 500,
  "message": "系统异常",
  "traceId": "TRACE_20260517143015999_a1b2c3d4e5f6"
}
```

服务端日志必须打印：

```text
traceId
title
fileName
fileSize
fileHash
exception stacktrace
```

关键日志示例：

```java
log.error("upload document failed, traceId={}, title={}, fileName={}, fileSize={}, fileHash={}",
        traceId, title, file.getOriginalFilename(), file.getSize(), fileHash, e);
```

这一步不改，后面只能猜。

---

# 三、第二步：重点修复重复文件并发上传

返回里有：

```json
"fileHash": "...",
"duplicateDocumentId": "DOC_20260509_963615"
```

说明服务端已经做了 **文件 hash 去重**。

压测时多线程上传同一个文件，很容易出现：

```text
线程A：计算 hash
线程B：计算 hash
线程A：查库，没有重复
线程B：查库，没有重复
线程A：插入成功
线程B：插入失败，唯一键冲突
```

## 推荐修复方式

### 方案 1：duplicate 判断 + 插入做幂等处理

伪代码：

```java
public UploadResult upload(String title, MultipartFile file) {
    String fileHash = calculateHash(file);

    Document existing = documentRepository.findByFileHash(fileHash);
    if (existing != null) {
        return buildDuplicateResult(existing, title, file);
    }

    try {
        Document doc = saveNewDocument(title, file, fileHash);
        return buildSuccessResult(doc);
    } catch (DuplicateKeyException | DataIntegrityViolationException e) {
        Document existingAfterConflict = documentRepository.findByFileHash(fileHash);
        if (existingAfterConflict != null) {
            return buildDuplicateResult(existingAfterConflict, title, file);
        }
        throw e;
    }
}
```

核心思想：

```text
并发插入冲突不应该返回 500
而应该重新查一次已有文档，然后返回 duplicateDocumentId
```

# 四、第三步：文件保存名不要用原始文件名

不要直接用：

```text
需求文档01_智能订单履约与售后协同系统.md
```

作为服务器保存文件名。

应该改成：

```text
DOC_20260516_289260.md
```

或者：

```text
fileHash.md
```

或者：

```text
UUID.md
```

推荐：

```java
String ext = getFileExtension(file.getOriginalFilename());
String storageFileName = documentId + "." + ext;
```

这样可以避免并发写同名文件冲突。

---

# 五、第四步：上传接口只做“轻处理”

上传接口里最好只做：

```text
接收文件
计算 hash
保存文件
写入 document 记录
返回 documentId
```

不要在上传接口同步做：

```text
文档解析
AI生成
复杂内容分析
```

解析任务应该异步化：

```text
上传成功
→ parseStatus=PENDING
→ 提交异步解析任务
→ 立即返回
```

如果你已经是这样，也要确认：

```text
异步任务提交失败不能影响上传成功
```

也就是说，即使解析任务入队失败，也应该明确返回可识别错误，而不是系统异常。

---

# 六、第五步：检查数据库唯一索引

如果有唯一索引，例如：

```sql
unique(file_hash)
```

这是合理的。

但是服务端必须捕获唯一键冲突。

你要重点搜日志：

```text
Duplicate entry
SQLIntegrityConstraintViolationException
DataIntegrityViolationException
DuplicateKeyException
```

如果出现这些，基本就定位了。

---

# 七、第六步：临时放宽连接池 / 线程池

如果是 Spring Boot，可以先临时加：

```yaml
server:
  tomcat:
    threads:
      max: 200
      min-spare: 20
    accept-count: 200

spring:
  datasource:
    hikari:
      maximum-pool-size: 30
      minimum-idle: 10
      connection-timeout: 30000
```

如果有异步解析线程池：

```yaml
ai-testops:
  async:
    core-pool-size: 8
    max-pool-size: 32
    queue-capacity: 500
```

但注意：**不要一上来只调大线程池**。如果根因是重复 hash 并发冲突，调线程池治标不治本。

# 八、JMeter 侧也做一个验证

为了确认是不是“同文件并发上传”问题，你可以做三组压测：

## A. 同一个中文文件

```text
当前文件继续压
```

如果偶发 500，记录。

## B. 同一个英文文件

```text
D:\perf\test.md
```

如果错误消失，说明可能和中文文件名 / 路径处理有关。

## C. 多个不同文件轮询上传

准备：

```text
D:\perf\file-1.md
D:\perf\file-2.md
D:\perf\file-3.md
D:\perf\file-4.md
```

如果错误明显减少，说明大概率是：

```text
同一文件 hash 并发去重逻辑有问题
```

# 九、推荐修复优先级

按这个顺序改：

```text
1. 业务 ID 改为日期 + UUID 后缀，降低 document/chunk/parse_result 唯一键碰撞风险
2. 后端异常响应和日志补全 traceId + stacktrace
3. 上传落盘文件名改为 documentId.ext，数据库继续保留原始 fileName
4. JMeter 上传数据改为 filePath/fileName/mimeType 三列 CSV
5. 显式暴露 Tomcat / Hikari 参数，按复压结果调优
6. 分别复压中文单文件、英文单文件、多文件轮询
```
