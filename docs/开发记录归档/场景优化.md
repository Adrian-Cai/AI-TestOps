从 4 个方向优化：**前端交互体验、页面视觉美化、异常场景测试、真实大模型联调后的 Prompt 调优**

# 一、前端交互细节优化

你的页面核心流程是：

```text
输入材料 / 上传文件
→ 文件解析
→ 查看解析结果
→ AI 生成测试用例
→ 校验结果
→ 人工编辑确认
→ 保存 / 导出
```

建议前端做成 **Step 步骤式交互**，不要把所有内容堆在一个页面里。

## 1. 步骤条设计

页面顶部固定一个步骤条：

```text
1 输入材料
2 解析结果
3 AI 生成
4 人工确认
5 保存导出
```

每一步需要有明确状态：

| 状态  | 展示效果              |
| --- | ----------------- |
| 未开始 | 灰色                |
| 进行中 | 蓝色 loading        |
| 成功  | 绿色对勾              |
| 失败  | 红色错误              |
| 可重试 | 显示“重新解析 / 重新生成”按钮 |

---

## 2. 输入区优化

输入区建议做成两个 Tab：

```text
Tab 1：粘贴需求文本
Tab 2：上传需求文件
```

### 文本输入优化

需要支持：

* 字数统计
* 最小输入长度校验
* 清空按钮
* 示例需求一键填充
* 输入内容预览
* 超长文本提示

示例交互：

```text
当前输入：2680 字
建议：需求内容超过 500 字后，AI 生成效果更稳定
```

---

### 文件上传优化

上传文件区域建议做成拖拽上传：

```text
拖拽文件到此处，或点击选择文件
支持 md / txt / doc / docx / pdf / ppt / pptx / xls / xlsx
单文件最大 20MB
```

上传后展示文件卡片：

```text
文件名：订单履约需求说明.docx
文件类型：docx
文件大小：1.8MB
文件 Hash：xxxxxx
上传状态：已上传
解析状态：待解析
```

文件上传前端要先做一次校验：

| 校验项   | 处理           |
| ----- | ------------ |
| 文件为空  | 禁止上传         |
| 格式不支持 | 提示支持格式       |
| 文件过大  | 提示最大限制       |
| 文件名过长 | 提示重命名        |
| 重复上传  | 提示是否复用已有解析结果 |

---

## 3. 解析结果页优化

解析完成后，不要只展示一大段 raw_text。建议分成 4 个区域：

```text
文档信息
元数据
正文预览
分块结果
```

### 文档信息卡片

展示：

```text
文档 ID
文件名
文件类型
解析状态
文本长度
Chunk 数量
上传时间
解析耗时
```

---

### 元数据展示

用 JSON Viewer 展示：

```json
{
  "Content-Type": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
  "title": "会员积分优惠券与营销活动规则引擎",
  "author": "产品团队",
  "created": "2026-05-02T10:00:00"
}
```

---

### 正文预览

正文预览建议支持：

* 搜索关键词
* 高亮关键词
* 折叠长文本
* 复制文本
* 查看完整文本
* 仅展示前 3000 字，避免页面卡顿

---

### Chunk 分块结果

建议用表格展示：

| Chunk ID  | 序号 | 所属章节 |  字数 | Token 估算 | 操作 |
| --------- | -: | ---- | --: | -------: | -- |
| CHUNK_001 |  1 | 订单创建 | 820 |      360 | 查看 |
| CHUNK_002 |  2 | 退款规则 | 950 |      420 | 查看 |

点击“查看”打开抽屉，展示该 chunk 的完整内容。

---

## 4. AI 生成页优化

AI 生成不要只放一个按钮，建议展示生成配置：

```text
模型：DeepSeek / Qwen / OpenAI
Prompt 模板：测试用例生成 v1.0
生成模式：正常 + 异常 + 边界
用例数量：10 / 20 / 30
覆盖维度：功能 / 接口 / 字段 / 权限 / 异常 / 边界
```

点击生成后展示：

```text
正在生成测试用例...
当前阶段：正在分析业务规则
预计生成内容：测试用例、风险标签、需求映射
```

生成完成后展示生成摘要：

```text
本次生成 18 条测试用例
正常场景：6 条
异常场景：7 条
边界场景：5 条
关联需求：12 个
高风险用例：4 条
校验结果：通过 16 条，警告 2 条
```

---

## 5. 人工确认页优化

测试用例不要只展示 JSON，建议表格 + 抽屉编辑。

表格字段：

| 状态  | 用例标题   | 优先级 | 类型   | 风险等级 | 关联需求    | 校验状态 | 操作           |
| --- | ------ | --- | ---- | ---- | ------- | ---- | ------------ |
| 待确认 | 正常提交订单 | P1  | 正常场景 | HIGH | REQ_001 | 通过   | 编辑 / 确认 / 驳回 |

点击编辑后打开右侧抽屉：

```text
用例标题
前置条件
测试步骤
预期结果
优先级
风险标签
关联需求
评审备注
```

每条用例支持：

```text
编辑
确认
驳回
删除
复制
重新生成单条
```

批量操作支持：

```text
批量确认
批量驳回
批量导出
```

# 二、页面美化优化

整体风格走：

```text
后台管理系统 + AI 工作台 + 数据卡片

```text

| AI 生成中 | 大模型正在分析需求并生成测试用例     |

# 三、更多异常场景测试

项目非常适合做“异常场景测试”，因为它涉及文件、解析、AI、JSON、数据库、人工操作。

可以按模块设计测试。

---

## 1. 文件上传异常

| 场景                | 预期结果         |
| ----------------- | ------------ |
| 上传空文件             | 提示文件不能为空     |
| 上传不支持格式 exe / zip | 提示文件格式不支持    |
| 上传超过大小限制文件        | 提示文件超过限制     |
| 上传文件名超长           | 提示文件名过长      |
| 上传中文文件名           | 正常保存和解析      |
| 上传特殊字符文件名         | 自动清洗或安全保存    |
| 重复上传同一文件          | 提示已存在或复用解析结果 |
| 上传损坏 PDF          | 解析失败并记录原因    |
| 上传加密 PDF          | 提示文件无法解析     |
| 上传扫描版 PDF 图片      | 提示未提取到有效文本   |
| 上传空白 Word         | 提示未提取到有效文本   |
| 上传多 Sheet Excel   | 正常提取工作表内容    |
| 上传 PPT 图文混排       | 尽可能提取文本内容    |

---

## 2. Tika 解析异常

| 场景          | 预期结果                  |
| ----------- | --------------------- |
| Tika 抛异常    | parse_status = FAILED |
| 解析结果为空      | 提示文档无有效文本             |
| 元数据为空       | 不影响主流程                |
| raw_text 超长 | 正常分块，不直接一次传给 AI       |
| 文件编码异常      | 尝试统一 UTF-8            |
| 表格文本顺序混乱    | 保留原始文本并提示可能需要人工检查     |
| PPT 页文本重复   | 清洗重复段落                |
| Excel 单元格合并 | 尽可能保留行列文本             |

---

## 3. 分块异常

| 场景                | 预期结果              |
| ----------------- | ----------------- |
| 文本长度小于 chunk_size | 生成 1 个 chunk      |
| 文本为空              | 不生成 chunk，提示失败    |
| 单段文本特别长           | 按长度强制切分           |
| chunk 数量过多        | 限制最大 chunk 数或分页展示 |
| chunk 内容重复        | 可做去重              |
| section_title 为空  | 使用默认章节名           |
| token_count 估算失败  | 使用字符数兜底           |

---

## 4. AI 调用异常

| 场景               | 预期结果                        |
| ---------------- | --------------------------- |
| API Key 未配置      | 提示模型配置错误                    |
| 模型接口超时           | generation_status = FAILED  |
| 模型返回 401         | 提示鉴权失败                      |
| 模型返回 429         | 提示请求频率过高                    |
| 模型返回 500         | 提示模型服务异常                    |
| 模型返回空内容          | 提示 AI 返回为空                  |
| 模型返回 Markdown    | 提取 JSON 或提示格式错误             |
| 模型返回非法 JSON      | 校验失败并保存原始输出                 |
| 模型生成字段缺失         | validation_result = FAILED  |
| 模型生成重复用例         | validation_result = WARNING |
| 模型生成与需求无关        | 标记低置信度或人工确认                 |
| 模型 hallucination | 通过 requirement_refs 校验发现    |

---

## 5. 测试用例校验异常

| 场景                     | 预期结果  |
| ---------------------- | ----- |
| case_id 为空             | 校验失败  |

| steps 为空               | 校验失败  |

| priority 非 P0/P1/P2/P3 | 校验失败  |
| requirement_refs 为空    | 警告或失败 |
| risk_level 非合法值        | 校验失败  |
| steps 不是数组             | 校验失败  |
| 重复 case_id             | 校验失败  |
| 重复 title               | 警告    |
| 用例数量为 0                | 生成失败  |

---

## 6. 人工确认异常

| 场景        | 预期结果                       |
| --------- | -------------------------- |
| 编辑后标题为空   | 前端禁止保存                     |
| 删除所有步骤    | 前端禁止保存                     |
| 重复确认同一用例  | 后端拒绝                       |
| 已驳回用例再次确认 | 后端校验状态                     |
| 并发编辑同一用例  | 使用 updated_at 或 version 控制 |
| 批量确认部分失败  | 返回失败明细                     |
| 评审备注过长    | 提示限制长度                     |
| 保存过程中网络中断 | 提示重试，不丢失本地编辑内容             |

---

## 7. 数据库异常

| 场景                | 预期结果                 |
| ----------------- | -------------------- |
| 文档不存在             | 返回明确错误               |
| document_id 重复    | 重新生成或返回冲突            |
| generation_id 不存在 | 返回错误                 |
| JSON 字段过长         | LONGTEXT 可承载，必要时截断摘要 |

| 确认用例失败            | 草稿状态不变               |
| 数据库连接失败           | 返回系统异常               |

# 四、真实大模型联调后的 Prompt 调优

真实联调后，发现模型常见问题不是“不会生成”，而是：

```text
生成格式不稳定
字段缺失
用例泛泛而谈
需求关联不准确
异常场景不足
边界值不具体
输出 Markdown 包裹 JSON
重复用例较多
```

所以 Prompt 要按问题逐步调优。

---

## 1. Prompt 不要一次性让模型做太多事

建议拆成两阶段：

```text
第一步：需求解析
第二步：测试用例生成
```

不要直接：

```text
输入原始需求 → 直接生成测试用例
```

更稳的是：

```text
原始需求
→ 提取结构化需求
→ 基于结构化需求生成测试用例
```

这样可控性更高。

---

## 2. 需求解析 Prompt 优化方向

目标是让模型先提取：

```text
需求点
业务规则
接口
字段约束
状态流转
异常场景
边界条件
风险点
```

### 优化版需求解析 Prompt

```text
你是一名资深测试分析师和需求分析师。

请从下面的需求文档中提取结构化需求信息。

要求：
1. 只能输出 JSON，不要输出 Markdown，不要输出解释说明。
2. 不允许编造需求文档中不存在的功能。
3. 每个需求点必须能追溯到原文片段。
4. 如果原文信息不完整，请在 risks 中标记“需求不明确”。
5. 需要重点提取业务规则、字段约束、状态流转、异常场景和边界条件。
6. requirement_id 从 REQ_001 开始递增。
7. priority 只能是 P0、P1、P2、P3。
8. risk_level 只能是 HIGH、MEDIUM、LOW。

输出 JSON 格式如下：
{
  "requirements": [
    {
      "requirement_id": "REQ_001",
      "title": "需求标题",
      "content": "需求内容",
      "priority": "P1",
      "risk_level": "HIGH",
      "source_text": "对应原文片段",
      "source_chunks": ["CHUNK_001"]
    }
  ],
  "business_rules": [
    {
      "rule_id": "RULE_001",
      "content": "业务规则",
      "related_requirement_ids": ["REQ_001"]
    }
  ],
  "api_list": [
    {
      "api_id": "API_001",
      "method": "POST",
      "path": "/api/order/create",
      "description": "接口说明",
      "related_requirement_ids": ["REQ_001"]
    }
  ],
  "field_constraints": [
    {
      "field_name": "amount",
      "constraint": "金额必须大于0",
      "related_requirement_ids": ["REQ_001"]
    }
  ],
  "exception_cases": [
    {
      "exception_id": "EX_001",
      "condition": "库存不足",
      "expected_behavior": "提交失败并提示库存不足",
      "related_requirement_ids": ["REQ_001"]
    }
  ],
  "risks": [
    {
      "risk_id": "RISK_001",
      "description": "风险描述",
      "risk_level": "HIGH",
      "related_requirement_ids": ["REQ_001"]
    }
  ]
}

需求文档内容如下：
{{document_text}}
```

## 3. 测试用例生成 Prompt 优化方向

测试用例生成要明确要求：

```text
正常场景
异常场景
边界场景
权限场景
状态流转场景
接口字段校验场景
并发/重复提交场景
```

### 优化版测试用例生成 Prompt

```text
你是一名资深测试架构师，擅长根据结构化需求设计高质量测试用例。

请基于下面的结构化需求信息生成测试用例。

要求：
1. 只能输出 JSON，不要输出 Markdown，不要输出解释说明。
2. 不允许生成与需求无关的测试用例。
3. 每条测试用例必须关联至少一个 requirement_id。
4. 每条测试用例必须包含明确的前置条件、测试步骤和预期结果。
5. 测试步骤必须具体可执行，不能只写“验证功能是否正常”。
6. 用例必须覆盖正常场景、异常场景、边界场景。
7. 如果存在权限、状态流转、金额、时间、库存、审批等规则，必须生成对应测试用例。
8. priority 只能是 P0、P1、P2、P3。
9. risk_level 只能是 HIGH、MEDIUM、LOW。
10. case_id 从 TC_001 开始递增。
11. 每个 step 必须包含 step_no、action、expected_result。
12. 不要生成重复标题的测试用例。
13. 优先生成高风险和核心链路用例。

输出 JSON 格式如下：
{
  "test_cases": [
    {
      "case_id": "TC_001",
      "title": "测试用例标题",
      "preconditions": [
        "前置条件1",
        "前置条件2"
      ],
      "steps": [
        {
          "step_no": 1,
          "action": "操作步骤",
          "expected_result": "预期结果"
        }
      ],
      "priority": "P1",
      "case_type": "正常场景",
      "risk_level": "HIGH",
      "requirement_refs": ["REQ_001"],
      "risk_tags": ["核心链路"]
    }
  ]
}

结构化需求如下：
{{requirement_extract_json}}
```

## 4. 让模型输出更稳定的技巧

### 技巧 1：强制 JSON-only

Prompt 里必须写：

````text
只能输出 JSON。
不要输出 Markdown。
不要使用 ```json 代码块。
不要输出解释说明。
````

---

### 技巧 2：枚举值写死

不要让模型自由发挥：

```text
priority 只能是：P0、P1、P2、P3
risk_level 只能是：HIGH、MEDIUM、LOW
case_type 只能是：正常场景、异常场景、边界场景、权限场景、状态流转场景、接口校验场景
```

---

### 技巧 3：字段缺失时要求填空数组

比如：

```text
如果没有识别到 api_list，请输出空数组 []，不要省略字段。
```

这样后端 JSON 解析更稳定。

---

### 技巧 4：先少量生成，再逐步扩展

不要一开始让模型生成 100 条用例。

建议：

```text
第一版：生成 10 条
第二版：按风险补充 10 条
第三版：针对未覆盖 requirement 补充
```

---

### 技巧 5：加覆盖率导向

在 Prompt 里加：

```text
请尽量保证每个 requirement_id 至少被 1 条测试用例覆盖。
如果某个 requirement 无法生成测试用例，请在 uncovered_requirements 中说明原因。
```

输出结构升级为：

```json
{
  "test_cases": [],
  "coverage_summary": {
    "covered_requirements": [],
    "uncovered_requirements": []
  }
}
```

## 5. 真实联调后的 Prompt 调优闭环

应该记录每次生成结果：

```text
prompt_version
model_name
input_snapshot
output_json
validation_result
人工评审结果
```

然后用这些数据反推 Prompt 问题。

### 常见问题与调优方式

| 问题          | 调优方式                       |
| ----------- | -------------------------- |
| 输出 Markdown | 加 JSON-only 约束，并在后端提取 JSON |
| 字段缺失        | 增加 JSON Schema 示例和必填字段说明   |
| 用例太泛        | 要求步骤必须可执行，禁止空泛描述           |
| 异常场景少       | 明确要求异常、边界、权限、状态流转          |
| 重复用例多       | 加“禁止重复标题”和后端重复检测           |
| 关联需求不准      | 要求每条用例必须引用 requirement_id  |
| 编造接口        | 加“不允许编造原文不存在的信息”           |
| 优先级混乱       | 给 priority 判定规则            |
| 风险等级混乱      | 给 risk_level 判定规则          |

## 6. 建议增加 Prompt 版本管理

 `prompt_template` 表已经有价值了。建议每次调优时不要直接覆盖，而是新增版本。

例如：

| template_code       | version | 说明             |
| ------------------- | ------- | -------------- |
| REQUIREMENT_EXTRACT | v1.0.0  | 初始版            |
| REQUIREMENT_EXTRACT | v1.1.0  | 增加 source_text |
| TEST_CASE_GENERATE  | v1.0.0  | 初始版            |
| TEST_CASE_GENERATE  | v1.1.0  | 增加覆盖率要求        |
| TEST_CASE_GENERATE  | v1.2.0  | 增加异常/边界/权限场景约束 |

这样你后面可以对比：

```text
同一份需求文档，用不同 Prompt 版本生成的用例质量差异
```

# 五、接下来具体做什么

## 第一阶段：先优化前端体验

优先做：

```text
1. 步骤条
2. 文件上传卡片
3. 解析结果预览
4. Chunk 表格
5. 生成结果表格
6. 用例编辑抽屉
7. 状态标签
8. Loading 和错误提示
```

---

## 第二阶段：补异常场景测试

先覆盖：

```text
1. 文件为空
2. 格式不支持
3. 文件过大
4. Tika 解析失败
5. raw_text 为空
6. AI 返回非法 JSON
7. 用例字段缺失
8. 重复用例
9. 人工确认重复提交
```

---

## 第三阶段：真实大模型联调

联调时重点记录：

```text
模型名称
Prompt 版本
输入文本长度
输出内容
是否 JSON 合法
用例数量
字段缺失数量
人工修改次数
最终通过率
```

---

## 第四阶段：Prompt 迭代

每次只改一个变量，例如：

```text
v1.0：基础生成
v1.1：增加 JSON-only 约束
v1.2：增加异常场景要求
v1.3：增加 requirement_refs 约束
v1.4：增加 coverage_summary
```

不要一次性改太多，否则不知道是哪一项起作用。

# 六、最终建议

现在可以把优化目标拆成这 4 条主线：

```text
前端：从能用变成好用
视觉：从 Demo 变成产品
测试：从正常链路变成异常完备
Prompt：从能生成变成稳定、高质量、可追溯
```

最关键的是：

> 平台不要只展示“AI 生成了测试用例”，而要展示“AI 生成结果经过了解析、校验、人工确认、版本记录和质量闭环”。

这个定位会比普通 AI Demo 高一个层级。
