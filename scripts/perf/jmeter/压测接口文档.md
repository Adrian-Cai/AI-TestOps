# AI-TestOps 主流程 JMeter 压测接口文档

日期：2026-05-17

## 1. 压测目标

本次只压测主流程中不依赖大模型的链路：

```text
文件上传 -> 文档解析 -> 人工确认草稿 -> 保存正式用例 -> JSON/Excel 导出
```

不纳入本次压测计时的步骤：

- `POST /api/ai-testops/ai/requirements/extract`：提取结构化需求
- `POST /api/ai-testops/testcases/generate`：生成测试用例草稿

这两个接口依赖大模型，耗时主要由模型服务、网络、token 数和排队情况决定。它们应该单独做 AI 链路耗时评估，不和后端基础容量压测混在一起。

## 2. 服务器配置与判断

| 项目 | 配置 |
| --- | --- |
| CPU | 4 核 |
| 内存 | 4 GB |
| 系统盘 | SSD 云硬盘 70 GB |
| 系统盘使用 | 34.2 GB / 70 GB，48.9% |
| 带宽 | 6 Mbps，约 0.75 MB/s |
| 当前 CPU | 5.416% |
| 当前内存 | 2325.833 MB |

判断：

- 这是入门型实例，适合验证 Demo/MVP 主流程容量。
- 文档解析依赖 Apache Tika，CPU 和内存会有短时压力。
- Excel 导出依赖 Apache POI，CPU/内存压力高于 JSON 导出。
- 6 Mbps 带宽是上传和下载场景的硬限制，批量导出不能只看 QPS，还要看下载文件大小和带宽吞吐。

## 4. 如何跳过大模型步骤

压测时不要调用结构化需求提取和草稿生成接口。推荐两种方式：

### 方案 A：压测前使用 MOCK/真实 AI 生成一次草稿

1. 非压测计时阶段完成上传、解析、结构化需求提取、生成草稿。
2. 查询 `PENDING` 状态草稿，整理为 `data/draft-groups.csv`。
3. 正式压测只调用批量确认和导出。

### 方案 B：直接造草稿数据

如果要完全避开 AI，可以直接准备数据库数据：

- `ai_testops_document`
- `ai_testops_document_chunk`
- `ai_testops_document_parse_result`
- `ai_testops_generation_record`
- `ai_testops_test_case_draft`

关键要求：

- `ai_testops_test_case_draft.review_status = 'PENDING'`
- `draft_case_id` 每次压测唯一，不要重复确认同一条草稿
- `steps_json` 是非空 JSON 数组，元素至少包含 `step_no` 和 `action`
- `expected_results_json` 是非空 JSON 字符串数组

`data/draft-groups.csv` 格式：

```csv
documentId,draftCaseIds,reviewer
DOC_20260517_000001,"[""DRAFT_20260517_000001"",""DRAFT_20260517_000002""]",perf_user
```

如果每次请求批量确认 5 条草稿，跑 `5 QPS * 10 分钟`，至少需要：

```text
5 * 600 = 3000 组草稿
3000 * 5 = 15000 条 PENDING 草稿
```

## 5. 接口清单

### 5.1 文件上传

| 项目 | 内容 |
| --- | --- |
| 接口 | `POST /api/ai-testops/documents/upload` |
| Content-Type | `multipart/form-data` |
| JMeter sampler | `01-upload_document 上传文档` |

请求参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `title` | string | 是 | 文档标题，压测中自动生成 |
| `file` | file | 是 | 上传的需求文档 |

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "documentId": "DOC_20260517_000001"
  }
}
```

JMeter 后置处理：

- JSON Extractor：`$.data.documentId` -> `documentId`
- Response Assertion：响应体包含 `"code":0`

变量传递方式：

1. 在上传接口下添加 `JSON Extractor`。
2. `Names of created variables` 填 `documentId`。
3. `JSON Path expressions` 填 `$.data.documentId`。
4. `Match No.` 填 `1`。
5. `Default Values` 建议填 `NOT_FOUND`，方便定位提取失败。
6. 后续接口中用 `${documentId}` 引用。

示例：

```text
/api/ai-testops/documents/${documentId}/parse
/api/ai-testops/documents/${documentId}
/api/ai-testops/documents/${documentId}/chunks
```

如果上传接口返回 `DOC_20260517_425766`，JMeter 实际发出的解析请求就是：

```text
POST /api/ai-testops/documents/DOC_20260517_425766/parse
```

说明：

### 5.5 批量确认草稿

| 项目 | 内容 |
| --- | --- |
| 接口 | `POST /api/ai-testops/testcases/drafts/batch-approve` |
| Content-Type | `application/json` |
| JMeter sampler | `01-batch_approve 批量确认草稿` |

请求体：

```json
{
  "draftCaseIds": [
    "DRAFT_20260517_000001",
    "DRAFT_20260517_000002"
  ],
  "reviewer": "perf_user"
}
```

注意：

- 该接口会把草稿写入正式用例表，也就是“人工确认 -> 保存正式用例”。
- 同一批 `draftCaseIds` 不要重复压测，否则已确认草稿会变成业务失败。

## 6. 压测场景

### 场景一：上传 + 解析

适合验证“很多用户批量上传需求文档，并触发解析”的容量。

流程：

```text
上传文档 -> 提取 documentId -> 解析文档 -> 思考时间
```

建议先使用 50 KB 到 300 KB 的 md/txt 文档，之后再用 300 KB 到 1 MB 的 pdf/docx/xlsx 做扩展测试。不要第一轮就直接压 50 MB 上限文件。

### 场景二：批量确认 + 导出

适合验证“AI 已生成草稿后，人工确认、保存、批量下载”的容量。

流程：

```text
读取一组 draftCaseIds -> 批量确认 -> JSON 导出 -> Excel 导出 -> 思考时间
```

建议：

- 每组 `draftCaseIds` 放 5 条草稿。
- 每个 document 对应 20 到 100 条正式用例。
- 如果重点是下载能力，单独跑 JSON 和 Excel，不要混在一起。

## 7. 指标目标

基于当前 4C4G、4GB 内存、6 Mbps 带宽，建议第一版指标如下：

| 场景 | 建议通过 QPS | 表现较好 QPS | Average | P95 | P99 | 错误率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 到 300 KB 文件上传 | 2 到 3 | 5 | <= 500 ms | <= 1 s | <= 2 s | < 1% |
| 100 到 300 KB md/txt 解析 | 2 | 3 到 5 | <= 1 s | <= 2.5 s | <= 5 s | < 1% |
| 300 KB 到 1 MB Office/PDF 解析 | 1 | 2 | <= 2 s | <= 5 s | <= 8 s | < 1% |
| 批量确认，5 条草稿/请求 | 5 | 8 到 10 | <= 500 ms | <= 1.2 s | <= 2.5 s | < 1% |
| JSON 导出，约 50 条用例 | 3 | 5 | <= 600 ms | <= 1.2 s | <= 2.5 s | < 1% |
| Excel 导出，约 50 条用例 | 1 到 2 | 3 | <= 1.2 s | <= 2.5 s | <= 5 s | < 1% |
| 混合主流程，不含 AI | 3 | 5 | <= 1 s | <= 3 s | <= 6 s | < 1% |

结论口径：

- `3 QPS` 稳定：当前入门型实例主流程可用。
- `5 QPS` 稳定：对当前配置来说表现较好。
- `8 到 10 QPS` 出现 P99 拉长：通常合理，需要继续看 CPU、内存、数据库、磁盘和带宽瓶颈。

## 8. 带宽估算

6 Mbps 约等于 0.75 MB/s。按 60% 保守可用带宽估算：

```text
可用吞吐约 0.45 MB/s
导出 QPS ~= 0.45 / 单次下载文件大小(MB)
```

| 单次导出文件大小 | 保守导出 QPS |
| ---: | ---: |
| 100 KB | 约 4.5 QPS |
| 500 KB | 约 0.9 QPS |
| 1 MB | 约 0.45 QPS |
| 5 MB | 约 0.09 QPS |

所以导出场景必须同时看 `Throughput` 和文件大小。文件越大，越容易先撞到公网带宽。

## 9. 阶段计划

| 阶段 | 目标 | 建议配置 | 通过标准 |
| --- | --- | --- | --- |
| Smoke | 验证脚本和接口可通 | 1 线程，30 秒 | 无脚本错误，核心接口 200/code=0 |
| 基线 | 建立初始数据 | 2 线程，5 分钟 | 错误率 < 1%，P95 达标 |
| 目标 | 验证合理容量 | 3 到 5 线程，10 到 15 分钟 | CPU < 70%，内存稳定，P99 达标 |
| 阶梯 | 找瓶颈点 | 5、8、10 线程，每档 10 分钟 | 找到 P99 或错误率突增点 |
| 稳定性 | 验证持续运行 | 目标线程数，30 到 60 分钟 | 无内存持续上涨、磁盘异常增长 |

## 11. 报告解读

JMeter HTML 报告中重点看：

- `Throughput`：吞吐量，可近似看作 TPS/QPS。
- `Average`：平均响应时间。
- `95th pct`：P95。
- `99th pct`：P99。
- `Error %`：错误率。
- `TX-upload-parse` 和 `TX-approve-export`：完整业务流程耗时。
- 单个 sampler：定位上传、解析、确认、JSON 导出、Excel 导出哪个慢。

输出结论建议：

| 项目 | 填写 |
| --- | --- |
| 场景 | 上传解析 / 确认导出 |
| 线程数 | 例如 2 |
| 持续时间 | 例如 300 秒 |
| Throughput | JMeter 报告 |
| Average | JMeter 报告 |
| P95 | JMeter 报告 |
| P99 | JMeter 报告 |
| Error % | JMeter 报告 |
| CPU / 内存 | 云服务器监控 |
| 带宽 | 云服务器监控 |
| 结论 | 通过 / 有条件通过 / 不通过 |
| 瓶颈 | CPU / 内存 / DB / Tika / Excel / 带宽 |
